## 1. Для стейкхолдеров (кратко)

### Что это в платформе

WowLance — **сервис рабочей комнаты**: команда, инструкции (снимок стратегии), задачи, лиды до Hot.  
Не CRM, не Jira, не кабинет стратегии и не регистрация пользователей.

### Что уже сделано (можно показывать на стенде)

| Возможность | Смысл для бизнеса |
|-------------|-------------------|
| Вход из Стратегии (FounderHandoff) | Кнопка «в WowLance» создаёт комнату со снимком стратегии |
| Тестовая «оплата» (entitlement) | Набор команды включается после stub-разрешения |
| Экран комнаты (React) | Фаундер/тимлид видят снимок, слоты, задачи, лиды |
| Слоты + roster | Назначение проверенных фрилансеров на места |
| Обновление стратегии | Тимлид Accept / Reject новой версии |
| Задачи + Quality Gate | Сдача с доказательством, приёмка/отклонение |
| Вход по JWT (stub/Keycloak-ready) | Готовность к общему логину платформы |
| Hot → CRM | Горячий лид уходит наружу (пока stub + outbox) |
| Контракты OpenSpec | Соседи могут стыковаться по схемам, не по «как у вас в коде» |
| Автотесты | 66+ pytest на срезах C1–C10 |

**Темп:** с ~10.10 по 17.10 закрыты срезы **C1–C10** (часть парами), отдельный репозиторий, FastAPI + React + PostgreSQL.

### Что предстоит

| Ближайшие срезы | Зачем |
|-----------------|--------|
| C11 Outbox `RoomCreated` | Сигнал соседям «комната создана» |
| C12 Unassign / reassign | Гибкость состава |
| C13 Room health → Стратегия | Витрина аналитики фаундера в Стратегии |
| C14+ | Боевые адаптеры (не stubs), matching, RBAC ролей |
| Согласование с CRM / Keycloak / Order / Strategy | Live endpoints вместо заглушек |
| Упакованный founder-demo сценарий | Один скрипт показа «кнопка → комната → команда → Hot» |

### Прогноз при текущей производительности

Ориентир команды: тимлид + стажёр(ы) + ИИ, **1–2 вертикальных среза в сутки** при параллели, с QA-отчётом на пару.

| Горизонт | Ожидание | Условие |
|----------|----------|---------|
| **1–2 недели** | C11–C13 + стабильный demo-path на stubs | Без ожидания боевых соседей |
| **3–5 недель** | Live JWT (Keycloak) + live handoff Strategy + entitlement от Order | Соседи отдают sandbox и контракты |
| **5–8 недель** | Hot в выбранную CRM first + сводки в Стратегию | Названа CRM, согласованы поля handoff |
| **Риск сдвига** | +2–4 недели | Нет владельца контракта у соседа / смена CRM mid-flight / брокера ещё нет (webhooks закрывают) |

**Итог для стейкхолдеров:** микросервис комнаты **уже существует и режет вертикальные сценарии на заглушках**. Узкое место для «платформы целиком» — не скорость WowLance, а **готовность Strategy / Talent / Order / CRM / Keycloak** принять те же контракты в бою.

## 2. Для смежных команд — как стыкуемся

### Принципы

1. **Своя БД у каждого сервиса** — чужие таблицы не читаем.  
2. **Контракт раньше кода** — YAML + JSON example в `contracts/<сервис>/` (реестр: `contracts/REGISTRY.md`; позже — общий OpenSpec platforms).  
3. **Синхронно:** HTTPS JSON за Gateway (`/internal/v1/…` для service-to-service, `/api/v1/…` для UI с JWT).  
4. **Асинхронно:** исходящие через **outbox** в PG WowLance → ваш consumer (брокер или webhook — как решит платформа).  
5. **Идемпотентность:** `handoff_id`, `publication_id`, `event_id` — повтор не создаёт дубликаты.  
6. **Пока сосед не готов** — stub-адаптер с тем же контрактом; замена stub → live без смены домена комнаты.  
7. **Пользователи:** общий Keycloak `sub`; в WL — shadow user; **регистрации в WL нет**.

### Карта обменов (кто что делает)

| Сосед | В WowLance | Из WowLance | Контракт / статус |
|------|------------|-------------|-------------------|
| **Strategy** | `FounderHandoff`, `StrategyPublished` | `RoomCreated` (C11), room-health (C13) | Handoff/Publish — **есть**; health — **в плане** |
| **Order / Payments** | `EntitlementGranted` (unlock staffing) | (при необходимости) ссылка на room | Entitlement — **есть** (stub POST) |
| **Talent** | `TalentRosterUpsert` | позже: сигналы рейтинга / termination | Upsert — **есть** (stub) |
| **CRM** | — | `HotLeadToCrm` (outbox) | **Контракт + stub**; нужен CRM first + поля |
| **Keycloak** | JWT Bearer на `/api/v1/*` | — | **JWKS/stub готов**; боевой realm — с платформой |
| **Gateway** | маршрутизация, CORS, JWT check | — | Нужен префикс `/wowlance` (или аналог) |
| **Storage** | URI SOP с **версией в пути** | свои uploads комнаты в prefix `wowlance/` | Политика согласована в ADR |
| **Jitsi** | — | URL встречи | Позже, не блокер |
| **Jira** | — | — | **Не входит** в 2.0 |

### Как работать со стыком на практике

```text
1. Берёте YAML + example из `contracts/<сервис>/` (см. REGISTRY.md)
2. Согласовываете breaking fields в чате владельцев (версия v1 → v1.1 / v2)
3. Песочница: ваш сервис ↔ наш stub endpoint или наш outbox poll/webhook
4. Контрактный тест (ваш consumer на наших examples + наш producer на вашем schema)
5. Переключение env: STUB=false → live URL / topic
```

**Внутренние URL (dev):**  
- Handoff: `POST /internal/v1/handoffs`  
- Entitlement: `POST /internal/v1/entitlements`  
- Strategy publish: по C5 (`StrategyPublished`)  
- Roster upsert: C6  
- Outbox Hot: пишется при mark-hot / handoff CRM (C9)  
- UI комнаты: React + `GET /api/v1/rooms/{id}` (Bearer при `AUTH_DISABLED=false`)

Точные поля — в соответствующих `*.v1.yaml` и `examples/*.json`.

### Чего ждём от вас (чек-лист соседа)

| Команда | Нужно от вас |
|---------|----------------|
| Strategy | Песочница handoff + publish; кто шлёт Accept UI только у нас |
| Order | Событие/вызов entitlement после тестовой оплаты |
| Talent | Поток verified → upsert (или мы poll’им ваш API) |
| CRM | **Имя first CRM** + обязательные поля Hot + URL create lead/deal |
| Keycloak | Client `wowlance-room`, JWKS, роли realm |
| Platform | Gateway route, решение брокер vs webhook, общий OpenSpec repo |

### Риски на стыках (честно)

- Пока CRM first не названа — Hot остаётся в stub (продукт комнаты при этом жив).  
- Без боевого Keycloak UI можно гонять на stub-token (уже сделано).  
- Room health в Стратегии появится после C13 — до того фаундер смотрит детали кнопкой «в комнату».

## 3. Оценка интеграции одним абзацем

WowLance 2.0 **готов как контрактно изолированный микросервис комнаты**: основные входящие потоки (стратегия, оплата-entitlement, roster, JWT) и исходящий Hot→CRM реализованы на **stubs + OpenSpec**, с тестами и UI-оболочкой. Для встраивания в большую платформу критичен не rewrite комнаты, а **календарь песочниц соседей** и фиксация CRM/Keycloak/Gateway. При текущем темпе внутренний контур C11–C13 — порядка **1–2 недель**; появление «боевых» стыков — **ещё 3–6 недель** после ответов смежников.
