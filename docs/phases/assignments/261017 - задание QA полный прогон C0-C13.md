## 2. Что не баг

| Наблюдение | Почему |
|------------|--------|
| Нет live Keycloak в compose | C8: stub JWKS / paste-token |
| `AUTH_DISABLED=true` по умолчанию | локальный demo |
| Internal (`/internal/v1/*`) без user Bearer | by design (service token later) |

| Document URI текстом, без скачивания S3 | C3 |
| Нет matching, полного RBAC ролей, earnings, termination, Meet ensure | C14+ |

| Нет экрана регистрации / sign-up | ADR-002: регистрация из WL не входит |
| `crm-stub:…` вместо Bitrix/amo | C9 stub; live CRM — согласование с соседями |
| После §11.2 забыли вернуть `AUTH_DISABLED=true` | не баг продукта; **обязательно вернуть** перед остальным UI-прогоном (см. 8.7) |

## 3. Сквозной «золотой путь» (одна комната)

Цель: одна `room_id` проходит весь контур. Фиксируй `room_id` / `task_id` / `slot_id` / `lead_id` в отчёте.

| # | Шаг | Ожидание |
|---|-----|----------|
| G1 | Handoff sale | `status=created`, есть `room_id` |
| G2 | UI Open room | имя, type, **Staffing locked** |
| G3 | Entitlement | `staffing_unlocked=true`; UI **unlocked** |
| G4 | Materialize slots | 200, seats `open` (sale → обычно 2× seller) |
| G5 | Roster upsert + Assign | слот `filled` |
| G6 | Task: Add → Start → Submit(proof) → Accept | `todo→in_progress→submitted→done` |
| G7 | Lead: Add → Mark hot → Hand to CRM | `crm-stub:…`, outbox HotLead |
| G8 | Unassign / Reassign | слот снова управляем |
| G9 | GET health + Publish | агрегаты ≠ нули где наполняли; outbox RoomHealthSnapshot |
| G10 | *(C11 / §13)* первый create + повтор handoff `already_exists` | create → ровно **1** `RoomCreated`; повтор → **не** вторая строка |

Параллельно: smoke Strategy publish → Accept (новый active snapshot; слоты **не** обязаны пересоздаваться — later).

**Порядок outbox-проверок на одной комнате:** сначала убедись, что после G7 есть `HotLeadToCrm`, после G9 — `RoomHealthSnapshot`, после G10 (если C11) — `RoomCreated`. Три разных `event_type`, строки не затирают друг друга (R2).

| # | Проверка | Ожидание |
|---|----------|----------|

| 11.3 | Повтор handoff `already_exists` | **не** вторая строка RoomCreated |
| 11.4 | Комната создалась ↔ outbox | атомарно (нет комнаты без события и наоборот при ошибке — по DoD) |
| 11.5 | Не ломает C1 | fingerprint / 409 на другой payload |
| 11.6 | Соседние outbox | HotLead / RoomHealthSnapshot — другие `event_type`, не затираются |
| 11.7 | Контракт | есть `RoomCreated.v1.yaml` + example; строка в `contracts/README` |
| 11.8 | Alembic | `alembic upgrade head` без ошибки; dual head — зафиксировать в отчёте |

Проверка SQL (пример):

```sql
SELECT event_type, status, idempotency_key, sent_at
FROM outbox_messages
WHERE event_type = 'RoomCreated'
ORDER BY sent_at;
```

Опционально: `GET /internal/v1/outbox?event_type=RoomCreated`, если endpoint есть.

## 17. Формат отчёта

Сохрани отчёт в `docs/` (имя вида `261017 - QA полный прогон C0-C13 отчёт.md`) или приложи в PR/чат:

1. **Стенд:** commit SHA `main`.  
2. **pytest:** `N passed` / failed list (ожидай ~100 на C0–C13).  
3. **C11 (§13):** Pass (уже в `main`).  
4. Таблица: ID проверки (`G1`, `7.4`, `11.1`/`13.x`…) → Pass / Fail / Blocked / Skip + комментарий; рядом фаза C*.  
5. **Баги:** steps, expected vs actual, severity (blocker / major / minor), SHA.  
6. Вердикт: **готово к релизу среза C0–C13** / **не готово** + блокеры.  
7. Опционально для стейкхолдеров: 5–7 строк «золотой путь прошёл / не прошёл» (founder-demo).  
8. Полные UUID golden room / slots / `idempotency_key` RoomCreated.
