## Короткий ответ на главный вопрос

**Не «Jira копирует фрилансеру трекер» как единственный мир.**

Рабочая модель:

1. **Операционные задачи комнаты** рождаются и закрываются в **WowLance** (простой трекер для фрилансера; операционка для тимлида).  
2. Каждая такая задача **зеркалится в Jira** (issue) для учёта, досок, отчётов и графиков.  
3. **Директор** почти не работает с доской задач — открывает **аналитику Jira** (и лёгкие итоги в кабинете WowLance).  
4. **«Я заработал»** — **не из Jira**. Это контур WowLance (начисления / биллинг), как в текущем продукте.

То есть направление по умолчанию:

```text
WowLance (операции + заработок)  ──синк──►  Jira (учёт + аналитика)
                 ▲                              │
                 │         при смене статуса     │
                 └────── webhook / API ◄─────────┘
```

Обратный поток из Jira → WowLance — **только** для полей, которые тимлид мог поменять в Jira (статус, дедлайн, assignee), с правилами приоритета. Фрилансер **не** входит в Jira.

## 1. Концептуальный уровень

### 1.1. Две системы — две ответственности

| Система | За что отвечает | Чем не является |
|---------|-----------------|-----------------|
| **WowLance Room** | Исполнение: люди в комнате, простые задачи, отчёты/доказательства, RBAC ролей, «я заработал» | Заменой Jira Software (портфели, сложные отчёты, все гаджеты) |
| **Jira** | Учёт и управление для TL/директора: борды, фильтры, дашборды, графики, история issue | Местом работы фрилансера и источником выплат |

### 1.2. Принцип «один объект — два лица»

Одна работа = **одна Task в WowLance** + **один Issue в Jira**, связанные id.

- Фрилансер видит только «лицо» WowLance.  
- Тимлид видит WowLance (день) и Jira (анализ / при желании доска).  
- Директор видит в основном «лицо» Jira-аналитики (+ короткие итоги в WowLance).

### 1.3. Почему не Jira → копирование фрилансеру как master

Если master — Jira:

- фрилансерский UX всегда «догоняет» чужой продукт;
- Quality Gate, чеклисты комнаты, расторжение, sale-специфика живут неудобно;
- директор и тимлид могут править issue так, что комната отстаёт;
- «я заработал» всё равно не из Jira — получится третий контур без ясности.

Поэтому: **комната = master операций**; **Jira = master аналитических представлений** над зеркалом задач (+ то, что завели только для eng-процессов компании, если понадобится позже).

### 1.4. Роли — разные «полноты» Jira

«Полный функционал Jira» в продуктовом смысле:

| Роль | Операции в WowLance | Jira |
|------|---------------------|------|
| Фрилансер | Да, простой трекер | **Нет доступа** (или только по исключению) |
| Тимлид | Да, вся операционка комнаты | **Полный** проект: доска, issue, фильтры, дашборды, отчёты |
| Директор | Минимум / только обзор комнаты без постановки задач | **Аналитика**: дашборды, графики, итоги; **без** обязанности вести день на доске |

Директору можно выдать в Jira роль с акцентом на **browse + dashboards** (без шума «назначить / закрыть / завести 40 задач»), если так решит PO — технически это группы прав Jira, не отдельный продукт.

## 2. Пользовательский уровень

### 2.1. Фрилансер

**Где:** только кабинет / комната WowLance.

**Задачи:**

- список «мои» / по статусам (новая → в работе → на проверке → готово);
- карточка: описание, дедлайн, чеклист, вложение отчёта;
- без эпиков, JQL, burndown, сложных досок.

**Аналитика (минимум):**

- «На этом проекте я заработал N»;
- «Всего на WowLance я заработал M»;
- без графиков команды и без Jira-отчётов.

Откуда цифры: журнал начислений WowLance (и/или Billing), **не** поля Jira.

### 2.2. Тимлид

**Где:** WowLance — основной рабочий день; Jira — полный контур анализа и при необходимости «тяжёлая» доска.

**Операционка (WowLance):**

- создать / назначить / принять / отклонить задачу и отчёт;
- состав команды, контроль исполнения в комнате;
- то, что связано с правилами комнаты (Quality Gate, доступы).

**Аналитика и полный Jira:**

- борды, backlog, графики, velocity/burndown (если настроены), фильтры, дашборды проекта;
- разбор «почему горит спринт» — в Jira;
- из комнаты — кнопка «Аналитика проекта» → нужный dashboard/board (SSO).

Тимлид **может** двигать issue в Jira; изменения статуса/срока **возвращаются** в карточку WowLance, чтобы фрилансер видел актуальное.

### 2.3. Директор

**Где:** не грузить оперативкой.

**В WowLance:**

- обзор комнаты / проекта на уровне «что купили, кто в команде, статус запуска»;
- короткие итоги (если нужны): горячие лиды, burn бюджета — по уже принятой логике директора;
- **без** ежедневной доски «кому какую задачу поставить» (это тимлид).

**В Jira:**

- дашборды и отчёты по проекту/портфелю;
- графики, итоги, срез здоровья исполнения;
- переход из WowLance одной кнопкой «Аналитика», без обязательного блуждания по issue.

Постановка задач директором в Jira **не** является основным сценарием (иначе снова операционка). Если директор хочет инициативу — через тимлида или редкое «запросить задачу» в комнате.

### 2.4. Сквозной пользовательский сценарий

1. Тимлид в WowLance создаёт задачу «Созвон с ICP» → назначает фрилансеру.  
2. Система создаёт issue в Jira (проект комнаты), пишет связь `wowlance_task_id` ↔ `PROJ-123`.  
3. Фрилансер видит задачу только в простом трекере, сдаёт отчёт.  
4. Тимлид принимает отчёт в WowLance → статус «готово» → sync в Jira Done.  
5. Директор утром открывает Jira-дашборд: сколько Done за неделю, burndown, загрузка — **не** разбирает каждую карточку фрилансера.  
6. Фрилансер в шапке видит обновлённый «я заработал» после начисления в WowLance.

## 3. Технический уровень

### 3.1. Источник правды по полям

| Данные | Master | Куда ещё |
|--------|--------|----------|
| Создание задачи комнаты, чеклист, отчёт, вложения доказательства | **WowLance** | В Jira — summary, description, status, due, assignee (упрощённо) |
| Статус исполнения (согласованная модель статусов) | **WowLance** как default; Jira может инициировать transition → обратно в WL | Двусторонняя синхронизация статусов |
| Сложная аналитика, борды, sprint reports | **Jira** | WowLance не дублирует |
| Суммы «я заработал» | **WowLance / Billing** | В Jira не источник |
| Членство в комнате, RBAC | **WowLance** | Assignee в Jira = mapping на `sub` / аккаунт Atlassian |

### 3.2. Направление синхронизации (детально)

**A. WowLance → Jira (основной поток)**

События: task created / updated / status changed / assignee changed / closed.

Действие: Jira REST API create/update issue, transition.

**B. Jira → WowLance (ограниченный обратный поток)**

Webhook: issue updated / transitioned.

Действие: обновить в WowLance только белый список полей (status, due date, assignee, priority).  
Не затирать отчёт, чеклист комнаты, файлы доказательств.

**C. Конфликты**

- Если изменили «почти одновременно» — побеждает **более новый timestamp** + запись в audit; при споре операционки комнаты приоритет у **тимлида в WowLance** (продуктовое правило).  
- Удаление issue в Jira не удаляет задачу комнаты молча — статус «разорвана связь» / алерт тимлиду.

### 3.3. Компоненты

```text
[React WowLance]
   │
[FastAPI Room]
   ├── Task service (PG)
   ├── Accrual / earned (PG)     ← фрилансерская аналитика денег
   └── Jira adapter
         ├── Outbox → create/update issue
         └── Webhook inbox ← Jira
[Jira Cloud/Server]
   ├── Project per Room (или per Client+Room)
   ├── Boards, Dashboards (TL + Director views)
   └── Permission scheme: Freelancer absent; Director dashboard-oriented; TL full
```

### 3.4. Идентичность

- Пользователи связаны через Keycloak `sub`.  
- В Jira — Atlassian account / mapping email↔sub (настройка платформы).  
- Фрилансеру **аккаунт Jira не обязателен**, если все операции через WowLance; issue может быть assigned на «технического» пользователя или на mapped account тимлида+поле «исполнитель WL» — предпочтительно **map фрилансера в Jira без выдачи ему UI** (лицензии Atlassian — отдельный вопрос к PO/закупкам).

### 3.5. Проект Jira на комнату

При handoff / активации комнаты:

- создаётся (или привязывается) Jira project / board;  
- создаются дашборды: «Director — Room X», «TL — Room X»;  
- в WowLance в `integrations` хранятся `jira_project_key`, URL дашбордов.

### 3.6. Что не синкать в Jira

- Персональные суммы заработка фрилансера.  
- Внутренние чаты комнаты (если появятся).  
- Документы SOP (storage + версия в пути) — в issue максимум ссылка.  
- SRM-лиды — другой контур (если sale).

## 5. Альтернатива (если PO настоятельно хочет Jira-master)

Возможен режим: тимлид ведёт задачи **только в Jira**, WowLance для фрилансера — **read-model + сдача отчёта**.

Минусы: сложнее Quality Gate и sale-процессы; выше зависимость от Jira; дольше MVP.  
Имеет смысл только если develop-команда уже 100% в Jira, а WowLance — тонкий портал исполнителя.

**Рекомендация для WowLance 2.0:** оставаться на **WowLance-master операций → Jira-зеркало для TL/Director analytics**.

## 6. Решения для фиксации с PO

1. Подтвердить: директор **без** ежедневной операционки задач.  
2. Подтвердить: фрилансер **без** UI Jira.  
3. Подтвердить: master задач комнаты = **WowLance**, sync **в** Jira.  
4. Нужен ли директору аккаунт Jira с полным edit или только dashboards?  
5. Лицензии Jira на каждого фрилансера — **нет** (цель) / да?  
6. Sale-задачи тоже в Jira или только develop-шаблон комнаты?

После ответов — перенести в итоговый документ и OpenSpec `JiraTaskSync`.
