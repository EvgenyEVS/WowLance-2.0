## 0. Одна фраза на старт

> **WowLance 2.0 — рабочая комната команды в общей платформе:** стратегия приходит снимком, команда исполняет, горячий лид уходит в CRM, фаундер смотрит здоровье комнаты. Сейчас — зрелый stub-MVP: полный путь уже крутится; live с соседями — после согласования контрактов.

## 2. Тезисы по разделам

### 2.1. Зачем 2.0

- 1.0 доказал **смысл комнаты** (роли, задачи, Hot, staffing).  
- 2.0 переносит **смыслы** в целевой стек платформы: FastAPI · React · PostgreSQL · OpenSpec · Keycloak/Gateway.  
- Цель — стыковаться с соседями по **контрактам**, не читать чужие БД.

**Акцент:** это не «переписали Django», а **сервис исполнения** в экосистеме.

### 2.2. Границы (таблица вслух)

| В WowLance | Не в WowLance |
|------------|---------------|
| Комната, слоты, roster, задачи + QG | Редактор стратегии → **Стратегия** |
| Прогрев лида → Hot → handoff | Сделки после Hot → **CRM** |
| Health / earned (сводка) | Основная витрина фаундера → **Стратегия** |
| Chat / Meet stubs | Боевой Jitsi SSO / биллинг → платформа / Order |

**Акцент:** «Мы не тащим CRM и кабинет стратегии внутрь комнаты — так задумано».

### 2.3. Путь фаундера (что показывать)

Говорить **по экрану**, не по слайдам API:

1. **Handoff** — комната создана со снимком стратегии (offer / audience / hot).  
2. **Entitlement** — staffing unlocked (пакет комнаты «оплачен» stub).  
3. **Команда** — слоты materialize → assign фрилансера.  
4. **Качество** — задача → proof → Accept → **Earned**.  
5. **Продажи** — лид open → hot → Hand to CRM.  
6. **Связь** — Meet-ссылка, чат в комнате.  
7. **Здоровье** — Room health + Publish snapshot (stub outbox в Стратегию).

**Акцент:** один `room_id` — весь цикл; без Keycloak/CRM в проде.

### 2.4. Контракты

- У каждого соседа свой каталог YAML + [REGISTRY](../../contracts/REGISTRY.md).  
- Статус сейчас: **aligned со stub-кодом**, не **agreed** с владельцем у соседа.  
- Пока нет `agreed` — безопасны stubs; опасно строить live и новые поля границы.

**Акцент:** «Готовы к согласованию; ждём владельцев / sandbox».

### 2.5. Честно про внешний вид

- UI сейчас — **рабочий stub-shell** (демо логики и интеграции).  
- Visual QA (C42): до parity с красивой комнатой 1.0 **ещё далеко**; волна C39–C41 — только CSS/chrome, без смены логики.  
- Если нужен «вау-вид» в тот же день — **второе окно: 1.0** как reference UX; 2.0 — как платформенный путь.

**Акцент:** не защищать зелёные кнопки как финальный дизайн; защищать **готовность домена и контрактов**.

### 2.6. Просьба к залу / next

1. Назначить **владельцев контрактов** у Strategy / Order / Talent / CRM / Keycloak.  
2. Не требовать live до `agreed`.  
3. Опционально: приоритет **UI parity** (C39→C41), если демо для внешних — «сначала лицо».

---

## 3. Акценты (что повторить 2–3 раза)

1. **Комната = исполнение**, не вся платформа.  
2. **Сквозной путь уже есть** на stubs.  
3. **Контракт раньше live.**  
4. **UI stub ≠ незавершённый продукт** — это этап; визуал отдельно планируется.

---

## 4. Чего не обещать

- Live Strategy / CRM / Talent «на следующей неделе» без `agreed`.  
- Pixel-perfect 1.0 уже в 2.0.  
- Биллинг лида / воронка CRM внутри WL.  
- Полноценный Keycloak realm в этом демо.

---

## 5. Запасные ответы (Q&A)

| Вопрос | Короткий ответ |
|--------|----------------|
| Почему не как 1.0 визуально? | Сначала контракты и путь; UI parity — отдельная волна (C39–C41). |
| Где смотрит фаундер аналитику? | Целевая витрина — в Стратегии; WL отдаёт health snapshot. |
| Когда live? | После `agreed` + sandbox соседа; stubs не блокируют разработку комнаты. |
| Сколько тестов? | Ориентир ~200+ pytest; полный QA-отчёт C0–C37 в docs. |
| RBAC? | Роли founder / teamlead / member есть; в демо по умолчанию ослаблен для простоты. |
