# Анализ: ТЗ «Сервис регистрации фрилансеров» vs WowLance 2.0

| Поле | Значение |
|------|----------|
| **Дата** | 2026-10-23 |
| **Источник ТЗ** | `260804 - TZ сервис регистрации фрилансеров Wowlance` (docx, ~04.08.2026) |
| **Наш канон** | [ADR-002](../canon/ADR-002-wowlance-2.0-platform-room.md) · [REGISTRY](../../contracts/REGISTRY.md) |
| **Вопрос** | Насколько далеко ТЗ от текущего проекта комнаты |

---

## Вердикт одной фразой

Это **не то же самое**, что WowLance 2.0.  
ТЗ описывает **соседний микросервис** (контур Talent / онбординг фрилансеров).  
Наш проект — **комната исполнения**. Они должны **стыковаться**, а не подменять друг друга.  
По замыслу платформы — **близко и комплементарно**; по коду/UI/контрактам комнаты — **далеко**.

| Ось | Дистанция | Оценка |
|-----|-----------|--------|
| 1. Общий замысел платформы | Комплементарно | **близко** (разные куски одной экосистемы) |
| 2. Архитектура | Похожий стиль, другая зона | **средняя** |
| 3. Пользовательский путь и UI | Почти не пересекаются | **далеко** |
| 4. Контракты и требования | Нужен маппинг / пересогласование | **средняя–далеко** |
| 5. Владение идентичностью (пароль/Keycloak) | Прямой конфликт с ADR-002 | **критично уточнить** |
| 6. Готовность стыка с текущим WL 2.0 | Roster stub ≠ полный Talent API | **средняя** |

---

## 1. По общему замыслу

### Что говорит ТЗ

- Микросервис **Freelancer Registration Service** — внешний контур платформы.  
- Делает: регистрация, профиль, MAU, рейтинг, availability, **API поиска** для Core.  
- **Не** делает: проекты, комнаты, задачи, платежи, логику найма (метчинг «в Core», поиск — у них).

### Что говорит ADR-002 / WowLance 2.0

- WowLance = **комната**: снимок стратегии, слоты, задачи, лиды до Hot, roster.  
- Явно **не входит**: «Верификация / стажировка фрилансеров» → **Talent**.  
- Регистрация пользователей в WL **запрещена** — только Keycloak / платформа.  
- Matching lite читает **локальный roster** после событий/upsert из Talent.

### Вывод

| | ТЗ 260804 | WowLance 2.0 |
|--|-----------|--------------|
| Роль в платформе | Talent / Registration | Room (Core-часть исполнения) |
| Главный пользователь | Фрилансер (онбординг) | Тимлид / фаундер / команда в комнате |
| Ценность | «Кто может работать на платформе» | «Как команда исполняет стратегию» |

**Дистанция по замыслу:** не конкуренты и не дубли.  
ТЗ ≈ то, что ADR называет **Talent**.  
«Core» в ТЗ ≈ наша комната (+ лиды/задачи), но в ADR Core уже **разрезан** (Strategy, CRM, Order, WL).

Шкала: **0 = то же самое, 10 = другой продукт** → по замыслу платформы **2–3** (сосед), по продуктовой поверхности комнаты **8–9**.

## 2. По архитектуре

### Совпадения (близко)

| Тема | ТЗ | WowLance 2.0 |
|------|----|--------------|
| Изоляция БД | Своя PostgreSQL | Своя PostgreSQL |
| Стек API | FastAPI (или Nest) | FastAPI |
| Контейнеры | Docker Compose | Docker Compose |
| Слои | API → service → repo | domain + api + adapters |
| Асинхрон с соседями | Да (события) | Да (outbox; брокер later) |
| Поиск/данные для найма | Отдельный сервис | Roster локально + контракт Talent |

### Расхождения (средняя–большая дистанция)

| Тема | ТЗ 260804 | WowLance 2.0 / ADR |
|------|-----------|---------------------|
| Auth | Свой `POST /register`, `/login`, password bcrypt, JWT сервиса | **Keycloak**; shadow User по `sub`; **нет** signup в WL |
| Брокер | **RabbitMQ** как обязательный | Outbox stub; брокер платформы TBD (не зафиксирован Rabbit) |
| Кэш | Redis обязателен для поиска | Нет Redis в MVP комнаты |
| Файлы | S3/Cloudinary портфолио | Object storage платформы (SOP); портфолио — зона Talent |
| Сосед «Core» | Один модуль «проекты/задачи/лиды» | Разнесено: WL + Strategy + CRM + Order |
| Matching | Логика найма в Core, поиск API у Registration | Matching lite **внутри** WL по локальному roster |
| Notification | Отдельный Notification Service (email verify) | Не в scope комнаты |

**Вывод по архитектуре:** тот же «микросервисный стиль платформы», но ТЗ рисует **более старую/учебную** картину (свой пароль, монолитный Core, RabbitMQ сразу).  
ADR-002 современнее по IAM (Keycloak) и границам сервисов.

Шкала дистанции архитектуры: **~5/10**.

## 3. По пользовательскому пути и интерфейсу

### Путь в ТЗ (фрилансер)

1. Регистрация (email + пароль)  
2. Подтверждение email  
3. Заполнение профиля (bio, skills, level, портфолио)  
4. Подписание MAU  
5. Availability Active/Busy  
6. Попадание в поиск / «ленту заказов»  
7. Рейтинг и журнал после задач  

UI по сути: **онбординг + кабинет профиля фрилансера**.

### Путь в WowLance 2.0

1. Фаундер: Strategy → FounderHandoff → комната  
2. Order → entitlement → staffing  
3. Тимлид: roster upsert (stub/Talent) → assign / match lite  
4. Задачи → QG → earnings / TaskAccepted  
5. Лиды → Hot → CRM  
6. Health → Strategy  

UI: **операционная комната**, не форма регистрации.

### Пересечение

| Сценарий | Есть в ТЗ? | Есть в WL 2.0? |
|----------|------------|----------------|
| Signup фрилансера | Да | **Нет (запрещено)** |
| Профиль skills/level | Да (SoT) | Тонкая копия в roster |
| MAU / оферта | Да | Нет |
| Рейтинг / acceptance rate | Да (SoT) | Нет (сигнал `TaskAccepted` наружу) |
| Экран комнаты / задачи | Нет (Core) | Да |
| Hot → CRM | Нет | Да |

**Дистанция UI/пути: ~9/10** — разные экраны, разные роли в фокусе.  
Единственная стыковка для UX тимлида: «выбрать человека из каталога Talent» → у нас сейчас stub roster + Suggest.

## 4. По контрактам и требованиям

### События ТЗ vs наши контракты

| ТЗ (Registration ↔ Core) | Ближайший аналог в WL 2.0 | Совпадение |
|--------------------------|---------------------------|------------|
| `FreelancerCreated` | нет прямого; косвенно User/Keycloak | ❌ |
| `FreelancerActivated` | близко к «можно в roster / verified» | 🟡 смысл есть, контракта нет |
| `FreelancerStatusChanged` | нет (`availability`) | ❌ |
| `FreelancerBlocked` | частично рядом с `MemberTerminated` (другое: выход из комнаты ≠ блок платформы) | 🟡 |
| `TaskCompleted` (Core → Registration) | у нас наоборот: **`TaskAccepted`** (WL → Talent) | 🟡 направление и имя другие |
| REST `GET /freelancers?skills&level` | `TalentRosterUpsert` + local `SlotMatch` | 🟡 другой паттерн (push upsert vs pull search) |
| `POST /register`, `/login` | запрещены в WL; у Talent должны идти в **Keycloak** по ADR | ❌ конфликт модели |

### Наш контракт Talent сейчас

- `TalentRosterUpsert` — тонкий stub (`freelancer_sub`, `display_name`, `skills`, `level`)  
- `MemberTerminated`, `TaskAccepted` — outbox из комнаты  
- Нет: MAU, rating, acceptance_rate, portfolio, availability, search API

### Функциональные пакеты ТЗ vs ADR

| Пакет ТЗ | Куда по ADR | В комнате 2.0 |
|----------|-------------|----------------|
| FR-REG (регистрация) | Talent + Keycloak | Не делать |
| FR-PRF (профиль) | Talent | Только тень в roster |
| FR-MAU | Talent / Legal | Не делать |
| FR-RTG (рейтинг) | Talent (вход: события из комнаты) | Отдаём TaskAccepted; рейтинг не считаем |
| FR-SRC (поиск) | Talent API → WL matching later | Matching lite local |
| FR-EVT | шина Talent↔Room | Частичный черновик |

**Дистанция контрактов: ~6–7/10.**  
Смысл стыка понятен, **имена, направление и SoT рейтинга нужно согласовывать заново** под ADR-002 (не принимать ТЗ 260804 as-is как контракт комнаты).

## 5. Идентичность и безопасность (критично)

ТЗ предполагает:

- пароль и JWT **внутри** Registration Service;  
- `User` с `password_hash` в БД сервиса.

ADR-002 / текущий WL:

- единый вход **Keycloak**;  
- WL и Talent — shadow по `sub`;  
- signup **не** в WowLance.

**Риск:** если реализовать ТЗ буквально, получится второй IAM рядом с Keycloak — платформенный долг.

**Рекомендация:** трактовать ТЗ как требования к **Talent**, но auth-часть переписать: регистрация через Keycloak (или IdP), а сервис хранит только профиль/MAU/stats.

## 6. Модель данных: пересечение

| Поле профиля ТЗ | Есть в WL roster stub? |
|-----------------|------------------------|
| full_name | display_name |
| level Junior/Middle/Senior | level (string) |
| skills[] | skills[] |
| bio, portfolio, phone | ❌ |
| rating, acceptance_rate | ❌ |
| mau_signed, availability | ❌ |
| email/password | ❌ (и не должны) |

Для live matching «как в ТЗ» комнате не хватает контракта обогащения roster (или pull search). Сейчас достаточно stub upsert.

## 7. Roadmap и сроки

ТЗ: MVP **~5 недель** только на Registration (+ расширение).  
WL 2.0: с ~09.10 уже C0–C33 stub комнаты.

Это **параллельные треки**.  
Registration не блокирует demo комнаты; блокирует **качество live-подбора** и «настоящий» Talent.

## 8. Что из ТЗ полезно комнате прямо сейчас

| Полезно перенять / учесть | Не тащить в WL |
|---------------------------|----------------|
| Событие «фрилансер activated/verified» → upsert roster | Signup/login/password |
| Поля skills/level как канон Talent | MAU UI |
| Вход рейтинга от accept задачи (у нас уже TaskAccepted) | Redis search API внутри комнаты |
| Явная граница: найм vs исполнение | «Лента заказов» в Registration |

---

## 9. Риски путаницы для команды

1. Назвать «Core» = WowLance и начать пилить регистрацию в репо комнаты — **нарушение ADR**.  
2. Принять события ТЗ без маппинга на `TalentRosterUpsert` / `TaskAccepted`.  
3. Сделать matching через live `GET /freelancers` до `agreed` с Talent — раньше времени.  
4. Дублировать рейтинг и в Talent, и в комнате.

## 10. Итоговая карта «насколько далеко»

```text
Платформа WOWLANCE
├── ТЗ 260804  ≈  Talent / Freelancer Registration   ← ЭТОТ ДОКУМЕНТ
├── Strategy
├── Order / Payments
├── CRM
├── Keycloak
└── WowLance 2.0  =  Room (наш репозиторий)         ← НАШ ПРОЕКТ
```

| Вопрос | Ответ |
|--------|--------|
| Это ТЗ на наш текущий репозиторий? | **Нет** |
| Это противоречит ADR? | Частично — **IAM/регистрация**; остальное согласуется как Talent |
| Нужно ли останавливать комнату? | **Нет** |
| Нужен ли стык? | **Да**, через Talent-контракты после переписывания auth под Keycloak |
| Насколько «далеко» в бытовом смысле? | **Другой сервис той же платформы** — рядом по карте, далеко по коду комнаты |

### Сводные баллы дистанции (0 = идентично, 10 = чужое)

1. Общий замысел платформы — **3**  
2. Архитектура — **5**  
3. UX / путь — **9**  
4. Контракты / FR-требования — **7**  
5. IAM / регистрация — **9** (конфликт, пока не переписан под Keycloak)  
6. Данные профиля vs roster — **6**  
7. Операционка комнаты (задачи, Hot, health) — **10** (в ТЗ отсутствует)

## 11. Практические следующие шаги (если ТЗ «живое»)

1. Зафиксировать на стейкхолдерах: **260804 = Talent**, не WowLance Room.  
2. Прогнать ТЗ через ADR-002: убрать свой password/JWT → Keycloak.  
3. Свести события к реестру:  
   - Talent → WL: `TalentRosterUpsert` / `FreelancerActivated` (новый draft);  
   - WL → Talent: уже есть `TaskAccepted`, `MemberTerminated`.  
4. Не включать FR-REG/MAU в бэклог комнаты.  
5. При согласовании Talent отдать им `contracts/talent/` + этот анализ как контекст.

---

**Итог:** ТЗ августа — про **сервис людей (регистрация/профиль/рейтинг)**; наш проект октября — про **сервис комнаты**.  
Для платформы они **должны встретиться на контракте Talent↔Room**; для текущей разработки комнаты документ **не является ТЗ продукта**, а **спекой соседа** с устаревшей моделью auth.
