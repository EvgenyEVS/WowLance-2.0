## 0. Вердикт по веткам (для контекста QA)

По коду на remote **готовы к ручному прогону**, блокеров «не стартовать» нет.

| Ветка | Что даёт | Замечание |
|-------|----------|-----------|
| **C2** `feature/c2-entitlement-unlock` | `POST /internal/v1/entitlements` → `staffing_unlocked=true`, идемпотентность / 404 / 409 | React не трогает |
| **C3** `feature/c3-room-read-shell` | `GET /api/v1/rooms/{id}` + UI бейдж locked/unlocked | Без C2 бейдж после handoff всегда **locked** |

**Как тестировать:**

1. **Предпочтительно (сквозной стенд):** влить обе ветки в локальную `qa/c2-c3` от `main` (или дождаться merge в `main`) — тогда проверяется путь handoff → entitlement → UI **unlocked**.  
2. **По отдельности:** C2 — только API; C3 — UI + GET (бейдж locked). Не считать багом C3, что unlocked не появляется без C2.

Автотесты (дымовые, не замена ручного):

```powershell
cd backend
.\.venv\Scripts\pytest -q
```

на соответствующей ветке / после merge.

|------------|--------|

## 3. Чеклист C2 — Entitlement (API)

Создать комнату:

```powershell
curl -s -X POST http://127.0.0.1:8000/internal/v1/handoffs `
  -H "Content-Type: application/json" `
  --data-binary "@contracts/strategy/examples/FounderHandoff.sale.json"
```

Запомнить `room_id`. Ожидание: `staffing_unlocked: false`, status `created` (или `already_exists`, если fixture уже гоняли — тогда смени `handoff_id` в копии JSON).

| # | Шаги | Ожидание | P |
|---|------|----------|---|
| E1 | `POST /internal/v1/entitlements` с новым `entitlement_id` + этот `room_id`, `source: stub` | **200**, `status: granted`, `staffing_unlocked: true` | блокер |
| E2 | Тот же JSON ещё раз | **200**, `status: already_granted`, `staffing_unlocked: true` (без ошибки) | блокер |
| E3 | Тот же `entitlement_id`, **другой** существующий `room_id` | **409** | блокер |
| E4 | Случайный несуществующий `room_id` | **404** | блокер |
| E5 | Без `entitlement_id` или не-UUID | **422** | высокий |
| E6 | После E1: повтор handoff **тем же** sale example | Не сбрасывает unlock: комната остаётся `staffing_unlocked: true` (проверить GET room или вторым grant уже не нужен — через GET если C3 на стенде, иначе через повтор E1/`already_granted` + при наличии inspect в БД/Swagger) | блокер |
| E7 | Свежий handoff (новый `handoff_id`) → до grant | Новая комната с `staffing_unlocked: false` | высокий |
| E8 | Два **разных** `entitlement_id` на одну `room_id` | Оба **200** (`granted`); флаг остаётся `true`. Не 409 | средний |
| E9 | `source: "invalid"` или лишнее поле в JSON | **422** | высокий |

## 4. Чеклист C3 — GET + React

| # | Шаги | Ожидание | P |
|---|------|----------|---|
| R1 | После handoff: `GET /api/v1/rooms/{room_id}` | **200**: name, type, timezone, founder_sub, offer/audience/hot_criteria из example, documents URI, `staffing_unlocked: false` | блокер |

| R7 | Vite proxy: UI ходит на `/api/...`, не на прямой CORS-сбой в консоли при живом backend | Нет failed fetch из‑за proxy | высокий |
