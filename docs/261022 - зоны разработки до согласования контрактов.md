**Останавливать разработку комнаты до согласования не нужно.**  
Stub-MVP и внутренний API — безопасны.  
Опасно считать граничные YAML финальными и строить на них глубокую логику / live.

Статусы в реестре: `draft` / `aligned` (с нашим кодом) ≠ `agreed` (с Strategy / Order / Talent / CRM / Keycloak).

## 2. Можно трогать, но только как stub (не «live»)

Граница уже есть в коде — **дорабатывать адаптер/outbox можно**, не подключать боевой сосед.

| Зона | Можно | Нельзя до `agreed` |
|------|--------|---------------------|
| Handoff / StrategyPublished | stub POST, Accept/Reject, rematerialize | live Strategy HTTP/bus |
| Entitlement / StaffingUnlocked | stub unlock, outbox row | live Order/Payments |
| Roster / Matching | local roster, matching lite | live Talent JOIN / ProfileChanged |
| Hot → CRM / deal-status | stub outbox + inbound | live CRM first / OAuth |
| JWT / service-token | stub JWKS, `X-Service-Token` | боевой realm + Gateway |
| RoomHealth publish | GET + outbox `RoomHealthSnapshot` | витрина в Strategy в проде |

**Правило:** менять payload граничного события — только через YAML в `contracts/<сосед>/` + запись в REGISTRY; не размазывать поля по UI «в обход».

## 3. Не углублять до согласования (высокий риск переделки)

| Зона | Почему ждать / сузить scope |
|------|------------------------------|
| **Новые поля FounderHandoff / Strategy snapshot** | Сосед часто переигрывает структуру offer/ICP/documents |
| **Deep CRM** (воронка, менеджерский кабинет в WL) | Вне ADR; поля Hot зависят от CRM first |
| **Live matching / полный Talent profile** | Нужен контракт ProfileChanged / verified |
| **Биллинг лида / счета из комнаты** | Order только за пакет комнаты |
| **Полный Gateway / multi-service auth** | Платформенное решение Keycloak |
| **Jira sync** | По ADR не обязательно для sale |
| **Смена имён событий «под arch»** без маппинга | Путаница (`PaymentSucceeded` vs `EntitlementGranted`) |

Если продукт просит фичу из этой таблицы — **тонкий stub + вопрос владельцу контракта у соседа**, не полноценная реализация.

## 4. Как ставить задачи стажёрам / ИИ

| Тип задачи | До согласования |
|------------|-----------------|
| UI / домен комнаты / тесты | ✅ давать |
| Новый граничный контракт v1 | ✅ только draft + stub, без «это финал» |
| Live adapter к Strategy/Order/CRM | ❌ блокер: sandbox + `agreed` |
| Breaking change граничного YAML | ❌ только после ping соседа / новая v2 |

Шаблон формулировки в задании:

> Контракт в `contracts/<сервис>/` — **draft**. Реализация через stub. Live не делать. Не ломать золотой путь G1–G10.
